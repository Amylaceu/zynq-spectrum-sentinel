## 开发顺序与验收

1. 先迁移现有识别/屏幕入口，显式选择100 MHz镜像并记录时钟，保留模型、采样率和原功能协议。只做PC回归，不启动新整机布线。
2. 复核100 MHz现有音频链及CDC/I/O报告，列出必须修复的具体路径。新RTL先做背压、复位、吞吐/数据一致性仿真；必要改动合并为一个有冻结清单的候选，再构建。
3. 用户已明确授权开发门槛改为 WNS/WHS≥0、TNS/THS=0；+1 ns 延后优化，原 Z10/T5 FAIL 保留。收据使用 development_nonnegative_v1，必须绑定实际产物哈希及六项审计全部通过的 development_review.json。对负裕量或未完成 CDC/I/O 检查仍拒绝部署；不以 false_path 掩盖失败。
4. 签核后先跑单音/三音/8192字回放、3.84 MSPS丢样/帧率回归，再做1 kHz/3秒喇叭测试。等待人工听音确认，然后进行5分钟FM监听。
5. 在同一100 MHz基线上继续Y4和Z1/Y5；优先通过PS实现演示、告警和Web功能。PS改动通常不需要Vivado重构建，但仍需软件与并发负载验收。

## 已完成的软件接续

monitor_x5支持显式 --image sentinel_v2_100m，使用V2驱动和对应时钟合同；默认仍是旧v1d，防止历史命令意外加载新镜像。新结果记录image与dsp_clock_hz。

tools/run_x5_board.py支持同一参数，沿用隔离部署和数据回收，v2产物使用独立测量标签；核对v2收据、HWH时钟、构建输入哈希，使用支持音频关闭核验的y3_postflight。未取得有效收据时在SSH前拒绝。

待签核后的入口（当前不能用来绕过门禁）：

```powershell
# 仓库根目录；按实际已加载位流填写板端路径；配置A须先获用户确认。
./.venv/Scripts/python.exe tools/run_x5_board.py --image sentinel_v2_100m --attempt 1 --lo 96400000 --confirm-configuration-a --preflight-bit <板端当前已验收位流完整路径>
```

## 后续修改的时间成本

- PS/UI/调度代码无需重新布局布线。
- 约束或实现策略修改可在输入未变时复用综合；RTL/IP改动至少重建受影响模块和顶层，再跑整机实现。
- T5本次日志中wait_on_runs耗时9分34秒；整个主构建日志创建至完成约12分钟，未包含独立审计。该值仅是复用综合的一次实测，不承诺后续相同耗时；RTL大改可能仍需数十分钟到数小时。
- 小改可以评估增量实现，收益依赖复用比例，不能保证收敛或固定加速倍数。布线完成后必须读取新报告，旧测量不能替代新版本验收。
